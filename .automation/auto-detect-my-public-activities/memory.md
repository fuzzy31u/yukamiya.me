## Review gate gotchas

- **Greptile edits its existing summary comment in place on re-review** — the `Reviews (N): Last reviewed commit` footer increments and the score is rewritten; it does not post a new comment. Polling for *new* comments therefore makes a finished re-review look like silence. On 2026-08-23 this run twice concluded Greptile had "never re-scored" while its summary already read 5/5. **Re-read the existing Greptile comment and check its score and footer commit, not the comment list.**
- A Claude Code Review run can take far longer than the first one on the same PR; a step sitting at `in_progress` is not a wedged workflow. Never push an empty commit to kick it.
- **Never pre-write `runs.last_review_gate`.** On 2026-08-30 it was written as "no PR opened this run" *before* the state PR was opened; the gate then ran, and the false claim shipped in the merge and needed a follow-up PR. Fill it in from the observed result, after the gate reports.
- **A state-only diff still deserves the gate.** PR #108 changed no code and the reviewers still found three real defects, two of which would have corrupted future sweeps.
- **When a candidate's classification changes, grep every file for the old wording.** "Rejected" for `archives/55718` lived in `state.json`, the `memory.md` topic bullet *and* the `memory.md` History line; fixing the first two left the third contradicting them, and both reviewers caught it.

## Cloud environment constraints

- **The "no egress" blocker was a misdiagnosis. It is the routine's cloud environment sitting on `Trusted` network access.** Four runs (2026-08-13 through 2026-08-30) recorded it as the environment having *no external egress at all*, because `403` came back on `CONNECT` for every host the sweep tried. It is not an outage and it does not clear on its own. Under `Trusted`, the environment allows only Anthropic's [default domain allowlist](https://code.claude.com/docs/en/cloud-environments#default-allowed-domains) — package registries, GitHub, cloud SDKs — and rejects everything else with `403` plus `x-deny-reason: host_not_allowed`. Every host this sweep needs is a Japanese media host outside that list, so *all* of them fail and the failure looks total. The tells that it is an allowlist and not an outage: npm, GitHub and `WebSearch` keep working, and `google.com` fails alongside `developers.cyberagent.co.jp` — a broken network would not spare the registry bypass.
- **Current setting: `aid` uses `Custom` network access.** The routine's environment is named **`aid`**, not `Default` — the docs describe a cloud icon reading "Default", which is why the control is easy to miss. It was changed from `Trusted` to `Custom` on 2026-09-02, briefly changed to `Full` on 2026-09-06, then returned to `Custom` the same day after the owner reassessed unrestricted egress as too risky. The 45 allowed host patterns cover every URL host currently stored in `about-content.js` plus the site itself; they are recorded in README, and the default package-manager domains remain included. Path: claude.ai/code → the routine (`trig_014KssRherH1RRBz94RrmzwC`) → **Edit routine** → the cloud icon under **Instructions** labelled with the environment name → hover the row and click its settings icon → **Network access: Custom**. Changes apply to new sessions.
- **The environment may be shared with other routines.** `Custom` bounds outbound access for every new session using `aid`; `obsidian-dia-extension` and `hrax` are separate environments. This sweep remains constrained by the public-HTTPS, read-only, no-secrets and prompt-injection controls in README's *Network safety boundary*.
- A run that hits `403 host_not_allowed` should name the host and verify that it is a legitimate source before adding the narrowest hostname or wildcard needed. It can also mean the session predates an environment change.
- If network access regresses, the sweep can still search, but **source-page validation and link verification cannot**. Never promote a candidate on search-summary evidence alone — record it as `detected` with the blocker and leave its validation to a run that can fetch. Leave `last_checked_at` stale for the author-page sources, and skip `QA Post Deploy` (its link findings would be unverifiable).
